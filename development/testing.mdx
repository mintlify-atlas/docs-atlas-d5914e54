## Test Directory Structure

```
vscode/
├── test/
│   ├── unit/              # Unit test infrastructure
│   ├── integration/       # Integration test infrastructure
│   ├── smoke/             # Smoke test suite
│   └── automation/        # UI automation helpers
├── src/
│   └── vs/
│       └── **/test/       # Unit tests alongside source
└── extensions/
    └── */test/            # Extension tests
```

<Info>
Unit tests are typically located in `test/` subdirectories next to the source code they test, following the pattern `src/vs/*/test/`.
</Info>

## Running Unit Tests

Unit tests run inside Electron with access to both Node.js and DOM APIs.

### Run All Unit Tests

<CodeGroup>
  ```bash macOS/Linux
  ./scripts/test.sh
  ```
  
  ```bash Windows
  scripts\test.bat
  ```
  
  ```bash npm
  npm run test-node
  ```
</CodeGroup>

The test script (scripts/test.sh:32):
- Automatically installs dependencies if needed
- Downloads Electron if not present
- Runs tests in an Electron environment
- Enables crash reporting to `.build/crashes/`

<Note>
The main test command in **package.json:13** intentionally shows a message directing you to use scripts from the `scripts/` folder.
</Note>

### Run Tests with Debug Mode

Enable debugging for tests:

```bash
./scripts/test.sh --debug
```

This opens an Electron window with Chrome DevTools, allowing you to:
- Set breakpoints
- Inspect variables
- Step through test code
- View console output

<Tip>
Use `--debug` when investigating test failures or writing new tests. The DevTools make it much easier to understand what's happening.
</Tip>

### Run Specific Tests

Use the `--run` or `--glob` option to run specific test files:

<CodeGroup>
  ```bash Run Specific File
  ./scripts/test.sh --run src/vs/editor/test/common/core/position.test.ts
  ```
  
  ```bash Pattern Matching
  ./scripts/test.sh --glob **/extHost*.test.js
  ```
  
  ```bash Grep Pattern
  ./scripts/test.sh --grep "findModel"
  ```
</CodeGroup>

From the test/unit/README.md:13, the `--grep` option allows running specific tests by name pattern.

### Run Tests in Different Environments

<Tabs>
  <Tab title="Electron (Default)">
    Tests run in Electron with full API access:
    
    ```bash
    ./scripts/test.sh
    ```
    
    This is the closest environment to how VS Code actually runs.
  </Tab>
  
  <Tab title="Browser">
    Run tests in real browsers (Chromium, WebKit, Firefox):
    
    ```bash
    npm run test-browser -- --browser webkit --browser chromium
    ```
    
    From **package.json:14**, this uses Playwright to run tests in multiple browsers.
    
    <Warning>
    Only tests from `common` and `browser` layers can run in browsers. Tests requiring Node.js APIs will fail.
    </Warning>
  </Tab>
  
  <Tab title="Node.js">
    Run tests in pure Node.js environment:
    
    ```bash
    npm run test-node -- --run src/vs/editor/test/browser/controller/cursor.test.ts
    ```
    
    Uses Mocha directly (**package.json:16**).
  </Tab>
</Tabs>

## Writing Tests

### Test File Naming

Follow these conventions:

- **Unit tests**: `*.test.ts` - Located in `test/` folders next to source
- **Integration tests**: `*.integrationTest.ts` - Also in `test/` folders
- **Compiled output**: Tests compile to `out/**/*.test.js`

### Test Structure

VS Code uses Mocha with TDD-style tests:

```typescript
/*---------------------------------------------------------------------------------------------
 *  Copyright (c) Microsoft Corporation. All rights reserved.
 *  Licensed under the MIT License. See License.txt in the project root for license information.
 *--------------------------------------------------------------------------------------------*/

import * as assert from 'assert';
import { MyClass } from '../myModule';

suite('MyClass', () => {
	
	test('should do something', () => {
		const instance = new MyClass();
		const result = instance.doSomething();
		assert.strictEqual(result, 'expected');
	});
	
	test('should handle edge cases', () => {
		const instance = new MyClass();
		assert.throws(() => instance.doSomethingBad());
	});
	
});
```

<Warning>
From .github/copilot-instructions.md:131-133:
- Don't add tests to the wrong suite
- Use `suite` and `test` consistently
- Look for existing patterns before creating new structures
</Warning>

### Assertion Best Practices

From .github/copilot-instructions.md:145:

<Tip>
Minimize the amount of assertions in tests. Prefer one snapshot-style `assert.deepStrictEqual` over multiple precise assertions, as they are much more difficult to understand and update.
</Tip>

Example:

<CodeGroup>
  ```typescript Good - Single Assertion
  test('parser output', () => {
    const result = parser.parse(input);
    assert.deepStrictEqual(result, {
      type: 'document',
      children: [...],
      metadata: {...}
    });
  });
  ```
  
  ```typescript Avoid - Multiple Assertions
  test('parser output', () => {
    const result = parser.parse(input);
    assert.strictEqual(result.type, 'document');
    assert.strictEqual(result.children.length, 3);
    assert.strictEqual(result.children[0].type, 'paragraph');
    assert.strictEqual(result.metadata.version, 1);
    // ... many more assertions
  });
  ```
</CodeGroup>

### Integration Test Example

For extension tests, use the Extension Host:

```typescript
import * as vscode from 'vscode';
import * as assert from 'assert';

suite('Extension Integration Tests', () => {
	
	test('should register command', async () => {
		const commands = await vscode.commands.getCommands();
		assert.ok(commands.includes('myExtension.myCommand'));
	});
	
	test('should process document', async () => {
		const doc = await vscode.workspace.openTextDocument({
			content: 'test content',
			language: 'typescript'
		});
		
		const result = await vscode.commands.executeCommand(
			'myExtension.process',
			doc
		);
		
		assert.deepStrictEqual(result, expectedOutput);
	});
	
});
```

## Troubleshooting

<AccordionGroup>
  <Accordion title="Tests fail with compilation errors">
    **Solution**: Ensure watch mode is running and code compiles:
    
    ```bash
    npm run watch
    # Wait for compilation to complete
    ./scripts/test.sh
    ```
  </Accordion>

  <Accordion title="Integration tests timeout">
    **Solutions**:
    1. Increase timeout in test configuration
    2. Check if VS Code is already running
    3. Verify Electron downloaded correctly:
       ```bash
       npm run electron
       ```
  </Accordion>

  <Accordion title="Browser tests fail">
    **Solutions**:
    1. Install Playwright browsers:
       ```bash
       npm run playwright-install
       ```
    2. Check browser-specific issues in test output
    3. Some tests only work in specific browsers
  </Accordion>

  <Accordion title="Tests pass locally but fail in CI">
    **Common causes**:
    - Platform-specific behavior (test on target OS)
    - Missing environment setup
    - Race conditions (add proper async handling)
    - Different Node.js versions
  </Accordion>

  <Accordion title="Memory errors during tests">
    **Solution**: Increase Node.js memory:
    
    ```bash
    export NODE_OPTIONS="--max-old-space-size=8192"
    ./scripts/test.sh
    ```
  </Accordion>
</AccordionGroup>
